# Custom language rules

This file contains user-maintained language preferences. Apply only the section that matches the requested output language. The user's current explicit instruction and the source meaning take precedence over these persistent preferences.

When adding or changing a rule, describe the observable wording or structure, the intended rewrite, any necessary exception, and the content it covers. Keep rules narrow enough to preserve real distinctions and source meaning.

When deriving preferences from user-provided examples, record the general wording principles and decision logic. Omit the original examples, recognizable paraphrases, and scenario-specific details from the maintained rules.

## Chinese / zh

### 中文表达的目标

普通中文交流应像耐心向对方说明事情：句子完整、用词日常、语气平和。按下面各条检查具体措辞，直接修改不符合的句子；仅换几个近义词或增加连接词，不算完成改写。正式文体按用户要求处理。

### 逐条检查表达方式

1. **把句子说完整。** 遇到省略过多的短句，补全理解所需的对象、动作和关系，让读者清楚什么东西怎么样、做了什么。上下文已经明确的内容无需重复。

2. **用日常动词说明事情。** 将抽象的判断标签、行政化表达和报告式简称，展开为具体对象的行为或状态。专业术语按需要保留，围绕术语的说明仍用普通人交流时会说的完整句子。

3. **保留自然的连接。** 按句意保留助词、条件词和转折词，让修饰关系和前后关系顺畅。条件应与相应动作连在一起，原本可选的操作应表达出选择空间。不要逐句机械补词。

4. **语气平和地接着说。** 以完整句子进入内容，解释或补充时直接承接前文，减少裁判式开场和刻意宣布重点的口吻。只有确有提醒必要时才使用提醒语；正式审查或摘要可按要求使用结论标签。

5. **自然地说明依据和局限。** 围绕讨论对象直接说清楚判断根据什么得出、还有什么没有确定。将压缩的依据标签和免责声明式措辞展开为日常叙述，使限定自然接在相关判断后面。

6. **按需要保留人称。** 上下文明确时，省略重复的人称和所属关系，让建议、对象或行动成为句子的中心。涉及责任、行动主体或可能产生歧义时，保留必要的指代。

7. **口语化仍要准确。** 动词应指向具体含义，避免含糊、夸张、拟人化或带价值评判的包装。语气词和限定词不能改变原有的确定性、效果程度或约束；完成检查也不等于确认结果。

8. **读顺以后再删重复。** 保留让句子自然的成分，删除相邻的同义重复。允许为清楚、顺畅的表达适当增加字数，不将完整叙述重新压缩成工作记录。

9. **直接解释，不预设误解。** 解释概念或数据时，直接说明它的含义、范围及与当前问题有关的关系。用户没有表达某种错误理解时，删除主动构造该误解再加以否定的句子；这种结构即使没有明说用户理解错了，也应删除。两个概念存在区别、可能被混淆或常见误解，本身都不足以成为主动纠错的理由。用户明确表达了相关误解时，针对其实际理解澄清；用户询问概念差异，或其明确提出的任务需要区分概念时，平实说明各自含义及完成任务所需的信息，不将概念说明写成对用户认识的纠正。

10. **结尾不补出担忧或承诺。** 说明当前状态时，围绕当前问题收尾。删除凭空引入严重结局再加以安慰、否定，或虚构结果保证再声明无法保证的表达；不因事情尚不确定，就主动扩大到整体失败或长期结论。必要的局限应具体说明当前信息能支持什么判断、还缺少什么信息。用户明确询问某种结果，或可靠依据表明相关风险会实质影响当前任务时，针对该问题或风险说明，保留有依据的不确定性。

### 特定情境的表达

- **判断是否预设误解时：** 结合用户当前问题及相关上下文，检查被回应的理解、担忧或评价是否由用户提出，或是回答该问题所必需的分析。不得仅凭否定句式、单独截取的结尾或纠正性措辞认定存在预设误解。缺少上下文时保留判断的不确定性。
- **用户询问做法是否正确时：** 直接回应其主动提出的评价请求，可以说明做法成立的条件、存在的问题，以及尚不足以得出判断的原因。保留与问题有关的否定判断和必要区分；改写生硬的语气，不删除评价本身。提出检查事项时直接说明理由，避免用无依据的高低对照抬高某个关注点。
- **说明变化时：** 围绕同一对象直接交代修改前后的状态及必要条件。只知道当前状态时，保留对过去状态和差异的不确定性。
- **承认疏漏时：** 用自然的第一人称说明漏做或漏讲的具体事项，承认已经发生的疏漏，避免仅表达事后的自我要求。确有疏漏时可简短道歉；单纯存在不确定性不需要道歉。
- **评价后补充限定时：** 先说明有依据的整体判断，再自然连接需要补充的细节，保留评价原有的程度。

### 明文禁止的表达和结构

- 禁止 `不是……而是……`、`直接做……不做……`、`只做……不做……`，命中后应改为平实的肯定表达。
- 删除先虚构观点、行动或选项，再通过否定它抬高结论的结构，以及先贬低一项再抬高另一项的人为对比。
- 删除用未执行动作衬托已执行动作的结构。保留与结果有关的未完成事项和验证范围。
- 用户输入和可靠依据均未提出的严重后果、极端风险或终局性判断，应删除整层内容，不通过安慰、弱化或改写继续保留。
- 来自用户实际问题或可靠依据的评价、对比、纠正和区分，应保留相关判断和事实差异；改写生硬的表达，不删除必要的事实和限定。

### 适用范围和边界

- 适用于所有可见中文回复、文档、标题、列表，以及代码注释、docstring、提交说明和报告中的中文内容。
- 本节主要调整表达方式。事实、来源、时间、数值、责任和不确定性遵循 `SKILL.md` 的共通要求；当前用户指令、原文含义及所需文体优先。
- 用户提供的示例只用于理解偏好和独立测试，不将原句、可辨认的改写或具体情境写入规则。

## 添加其他语言

为新语言增加一个使用语言名称和语言代码的二级标题，并包含以下内容：

- 需要识别的原文或表达结构。
- 推荐的改写方向。
- 需要保留的真实对比、术语或体裁特征。
- 适用的内容范围。
